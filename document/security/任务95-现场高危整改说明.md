## 三、8761/8762：Eureka

### 1. 先识别现场包

本地 ER `scripts/eureka/service.sh` 指向独立 `eureka/dwbi-eureka-0.1.jar`，用 `peer1/peer2` 启动两节点，不能拿业务模块的 Eureka 客户端版本推断服务端版本。
现场对实际 JAR 执行只读检查（替换绝对路径）：

```bash
unzip -l /实际路径/dwbi-eureka-0.1.jar | grep -E 'spring-boot-[0-9]|spring-security|application.*yml|bootstrap.*yml' | head -c 4000
```

同时确认启动脚本、外部 YAML、环境变量、端口及 peer 间注册地址。配置内容可能含凭据，不将原文复制到工单或日志。

### 2. 方案 A：有服务端源码时启用原生认证

在 **Eureka 服务端工程** 添加依赖，版本由其现有 Spring Boot/Cloud BOM 管理：

```xml
<dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-security</artifactId>
</dependency>
```

以下配置类适用于使用 Spring Security 4/5、`WebSecurityConfigurerAdapter` 的旧工程，放在启动类能够扫描到的包下；不能原样用于 Boot 3/Security 6：

```java
import org.springframework.context.annotation.Configuration;
import org.springframework.security.config.annotation.web.builders.HttpSecurity;
import org.springframework.security.config.annotation.web.configuration.EnableWebSecurity;
import org.springframework.security.config.annotation.web.configuration.WebSecurityConfigurerAdapter;

@Configuration
@EnableWebSecurity
public class EurekaSecurityConfig extends WebSecurityConfigurerAdapter {
    @Override
    protected void configure(HttpSecurity http) throws Exception {
        http.authorizeRequests().anyRequest().authenticated()
            .and().httpBasic()
            .and().csrf().ignoringAntMatchers("/eureka/**");
    }
}
```

注意：`/eureka/**` 仅忽略 CSRF，**不能 permitAll**。控制台和协议接口均须认证。
Boot 2.x 服务端配置：

```yaml
spring:
  security:
    user:
      name: ${EUREKA_USER}
      password: ${EUREKA_PASSWORD}
```

若确认服务端为 Boot 1.5.x，用户属性应使用顶层 `security.user.name/password`，不是 `spring.security.user`。若已有自定义用户服务，应对接该服务，不能假设以上默认用户配置生效。
两节点使用相同的专用注册凭据，凭据通过现场受限配置/启动环境注入，不写入 Git。

### 3. 方案 B：仅有旧 JAR 时用 Nginx Basic Auth

该方案无需改 JAR 依赖，但需要维护窗口协调端口及脚本：

| 原外部端口 | 新的 JAR 监听 | Nginx 监听 |
|---|---|---|
| 8761 | `127.0.0.1:18761` | `11.8.168.69:8761` |
| 8762 | `127.0.0.1:18762` | `11.8.168.69:8762` |

先为两个 Java 启动命令分别补 `--server.address=127.0.0.1 --server.port=18761` / `18762`；脚本的 PID 探测、等待端口、停止和状态检查也必须改为新端口，不能继续把 Nginx 的 8761 当成 Java PID。
若 `eureka.instance.nonSecurePort` 被显式设置，调整实例元数据与新部署匹配。节点互联的 `defaultZone` 显式指向下面有认证的 8761/8762，避免 `${server.port}` 改动导致自注册/互联走错端口。

创建口令文件（需要 htpasswd 工具，交互输入口令，不用 `-b` 在命令行传密码）：

```bash
sudo htpasswd -c /etc/nginx/eureka.htpasswd eureka_service
```

仅首次创建使用 `-c`；文件由 root 管理，授予 Nginx 工作进程组只读权限（例如 0640，组名以现场为准）。两端口共用该文件。
在 Nginx `http` 配置内增加以下两个 server，先确认该地址/端口没有其他代理占用：

```nginx
server {
    listen 11.8.168.69:8761;
    server_name _;
    auth_basic "Eureka";
    auth_basic_user_file /etc/nginx/eureka.htpasswd;
    location / {
        proxy_pass http://127.0.0.1:18761;
        proxy_set_header Host $http_host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header Authorization "";
    }
}
server {
    listen 11.8.168.69:8762;
    server_name _;
    auth_basic "Eureka";
    auth_basic_user_file /etc/nginx/eureka.htpasswd;
    location / {
        proxy_pass http://127.0.0.1:18762;
        proxy_set_header Host $http_host;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header Authorization "";
    }
}
```

清除传向 JAR 的 Authorization 不影响 Nginx 自己的认证，该方案假定旧 JAR 没有原生认证。不要与方案 A 的原生认证混用本模板。
原 Java 停止并迁移到内部端口后，执行 `nginx -t`，通过后按现场服务管理方式 reload/start。
此 HTTP 示例对应现有地址，Basic Auth 不加密传输；生产应配合可信网络隔离，具备证书后在入口启用 TLS，客户端同步用 HTTPS 并配置信任链。

### 4. 两种方案都必须修改客户端

盘点实际生效配置，不仅修改源码 resources：

- 数据分析：`deploy-package/config` 中主系统、SEO、报表、指标、可视化等所有启用 Eureka 的模块。
- ER：portal、register 的现场外部配置。
- Eureka 两节点彼此注册的配置。
- 其他项目若实际使用这两台 Eureka，也纳入盘点。Nacos 客户端不属于此名单。

业务客户端的合并配置示例：

```yaml
eureka:
  client:
    service-url:
      defaultZone: http://${EUREKA_USER}:${EUREKA_PASSWORD}@11.8.168.69:8761/eureka/,http://${EUREKA_USER}:${EUREKA_PASSWORD}@11.8.168.69:8762/eureka/
```

peer1 的 `defaultZone` 指向带凭据的 8762，peer2 指向带凭据的 8761；保留原集群的其他设置。
如原文件使用 `serviceUrl` 命名，沿用并修改其 `defaultZone`，不要重复添加两套配置。
Spring Eureka 客户端对同一列表采用第一套凭据，因此两个节点不要配置不同密码。密码包含 URI 特殊字符时必须正确编码；可生成足够长的十六进制随机口令避免编码歧义。不要打印完整注册地址，因为 URL 含凭据。

建议先给客户端准备并加载凭据，再切服务端认证。切换前记录实例清单；切换后必须观察至少两个实际心跳周期，并覆盖一次完整注册/重启验证。
如果旧服务端不能容忍提前发送凭据，应在维护窗口一起切换，不能以保留匿名接口作为长期兼容办法。

### 5. 验收

- 无凭据和错误凭据访问 `/`、`/eureka/apps` 应返回 401/403，不能返回注册表。
- 合法客户端可读取注册表、注册、续约；两个节点同步正常，所有业务实例恢复 UP。
- 代理方案中 Java 必须只监听 `127.0.0.1:18761/18762`；从其他主机无法直接访问内部端口。
- 从非白名单地址无法访问管理端口。防火墙限制与认证分别验收。

## 四、8848：Nacos 鉴权与默认身份修复

### 1. 确认实际版本、依赖和配置来源

在现场启动日志/控制台确认 **服务端** 版本，检查实际 `conf/application.properties`、容器环境变量、服务启动参数和持久化数据库。客户端 JAR 版本不能当服务端版本。
先备份 Nacos 数据库、配置文件及集群列表，盘点正在使用的 namespace、服务注册与配置拉取客户端。
本地 Nexus 交付配置中 `gk-auth`、`gk-system`、`gk-audit`、`gk-gateway`、`gk-bridge` 有 Nacos discovery 配置，但地址不等于报告地址；需现场确认哪些模块实际指向 `11.8.168.69:8848`，不能机械修改所有工程。

### 2. 服务端配置（适用于 Nacos 2.1/2.2 系列参数体系）

修改每个 Nacos 节点实际加载的 `conf/application.properties`。将下面三个 `REPLACE_...` 替换为现场生成的值，**不能直接使用占位符启动**：

```properties
nacos.core.auth.system.type=nacos
nacos.core.auth.enabled=true
nacos.core.auth.enable.userAgentAuthWhite=false
nacos.core.auth.server.identity.key=REPLACE_WITH_PRIVATE_HEADER_NAME
nacos.core.auth.server.identity.value=REPLACE_WITH_RANDOM_IDENTITY_VALUE
nacos.core.auth.plugin.nacos.token.secret.key=REPLACE_WITH_BASE64_TOKEN_SECRET
```

身份 key 是合法 HTTP header 名，建议由字母、数字、连字符组成；value 使用足够长随机值。不要继续使用默认 `serverIdentity` / `security`。
Token 签名密钥独立生成，使用至少 32 字节随机数据的 Base64 编码；不要复用管理员口令或 identity value。
所有集群节点的这三项保持一致，存放于受限配置文件，不发到群聊、不写入仓库。

可在受限运维目录生成新值（以下命令在当前目录创建三个文件，不输出密钥）：

```bash
umask 077
printf 'X-Nacos-%s\n' "$(openssl rand -hex 16)" > nacos-identity-key.txt
openssl rand -hex 32 > nacos-identity-value.txt
openssl rand -base64 32 > nacos-token-secret.txt
```

将文件内容通过受控方式分别写入对应配置，分发到全部节点。完成后按现场密钥管理规范保管/移除临时文件。

版本区别：

- 1.4.1～2.0.4 的 Token 属性名是 `nacos.core.auth.default.token.secret.key`，不能只添加新版属性名；identity 参数从 1.4.1 起支持。
- 若版本更早，或实际版本存在未修复的鉴权绕过，不把以上配置当成补丁；先网络隔离，再选与现场 JDK/SDK 兼容且已修复的受维护版本做升级测试。
- Nacos 3.x 的控制台和管理接口/端口模型不同，不直接套本 2.x 模板。
- 容器部署需修改实际 compose/编排环境配置并重建实例，避免只编辑容器内文件后重启丢失。参数映射按对应镜像版本核对。

Nacos 部分鉴权参数支持动态生效，因此不能假设“改配置但没重启就不会影响业务”。应提前准备客户端并在维护窗口统一切换；更换签名密钥会使旧 Token 失效。

### 3. 用户及客户端

修改默认管理员密码，检查未知管理员/角色；给业务创建非管理员专用账号并授予所需 namespace 的配置/注册权限。
如证据显示配置已被读取或账号被篡改，保留日志，清理异常账号，并轮换受影响的数据库/第三方凭据。

Spring Cloud Alibaba 客户端，合并到原有配置，不覆盖原 namespace/group：

```yaml
spring:
  cloud:
    nacos:
      discovery:
        # 保留原 server-addr、namespace、group
        username: ${NACOS_USERNAME}
        password: ${NACOS_PASSWORD}
      config:
        # 仅使用 Nacos 配置中心的模块才加此段
        username: ${NACOS_USERNAME}
        password: ${NACOS_PASSWORD}
```

如使用 `bootstrap.yml` 提前读取 Nacos 配置，凭据也必须放在 bootstrap 阶段可获得的位置，不能仅存在于尚未拉取到的 Nacos 配置里。
直接使用 Java SDK 的程序在创建 ConfigService/NamingService 的 Properties 中设置 `username/password`；外部脚本需先登录获取 Token，再执行授权 API。
客户端用户名/密码与 `server.identity`、Token 签名密钥是三种不同用途，**不能把服务端密钥发给客户端代替登录**。

### 4. 网络控制

| 服务/端口 | 允许来源 |
|---|---|
| Eureka 8761/8762 | 实际业务客户端服务器、peer、指定运维主机 |
| Nacos 8848 | 实际客户端服务器、集群节点、指定运维主机 |
| Nacos 2.x 默认 9848（客户端 gRPC） | 实际客户端服务器及必要节点 |
| Nacos 2.x 默认 9849、7848（节点通信） | Nacos 集群节点 |
| 代理方案的 18761/18762 | 仅本机回环 |

Nacos 额外端口以实际版本、偏移配置和监听结果为准。不要只封 8848 却暴露节点通信端口；也不要封掉客户端需要的 9848。
将此表交给现场网络管理员，在现有防火墙/安全组中落地明确源 IP/CIDR 白名单。未知现场 zone、链顺序及管理网段时，不执行一条“全端口拒绝”的通用脚本，以免切断业务或运维。

### 5. 只读复测

在允许连接但不带登录凭据的测试主机上，检查报告的两个入口及默认身份绕过：

```bash
curl --max-time 10 -sS -o /dev/null -w '%{http_code}\n' 'http://11.8.168.69:8848/nacos/v1/auth/users?pageNo=1&pageSize=1'
curl --max-time 10 -sS -o /dev/null -w '%{http_code}\n' -H 'serverIdentity: security' 'http://11.8.168.69:8848/nacos/v1/auth/users?pageNo=1&pageSize=1'
curl --max-time 10 -sS -o /dev/null -w '%{http_code}\n' -H 'User-Agent: Nacos-Server' 'http://11.8.168.69:8848/nacos/v1/auth/users?pageNo=1&pageSize=1'
```

预期拒绝访问，不返回用户列表；如现场也映射根路径 `/v1/auth/users`，必须一并复测。若返回 200，先检查是否只是登录页面/统一错误包装，再由扫描人员在受控位置核对响应，不能把口令散列等敏感内容复制进普通日志。
还需验证无 Token 不能读取实际受保护的配置；合法业务账号能完成配置拉取和服务注册，普通账号不能列举所有用户或创建管理员。不要仅以首页出现登录框作为通过。
最后使用原扫描器复扫 4 个端口，并保留已脱敏的请求路径、响应状态、修复时间及业务验证记录。

## 五、切换失败处理

先保留服务与网络日志，检查凭据是否实际注入、配置优先级、客户端兼容性及集群密钥一致性。业务异常时在网络隔离持续有效的前提下，按备份恢复对应服务配置/版本；Eureka 代理方案需连同端口、脚本和 peer URL 成套恢复。
不要为快速恢复长期打开匿名访问；9090 的注册/找回密码接口已确认现场不用，不应作为业务恢复手段重新启用。
