# Agent Key File Handler 全量迁移设计

## 1. 目标与范围

将 `agentKeyFileHandler-2.1.0.jar` 的全部业务能力复写并迁移到本仓库主系统：

- 后端承载模块：`org-tribe-system`；
- 前端承载模块：`org-tribe-view`；
- 数据库：Vastbase G100 V2.2；Vastbase 的 Schema 与原 MySQL Schema 一一对应；
- 迁移原则：JAR 的字段顺序、时间转换、重复周期覆盖范围、固定国库编码、状态语义和手工过程调用属于业务基线，禁止凭经验改写；目录兼容、安全解压、批量写入、原子回滚、限流和状态追踪只作为不改变成功结果的技术优化；
- 不迁移原 JAR 的 EasyUI 页面、MySQL 专有 SQL、硬编码文件路径和明文配置。

本设计覆盖 KEY 与 TIMS 两个来源域，以及相关配置、监控和手工加工调用。JAR 中已被页面注释且本次没有真实 EDW 对象支撑的收入/支出人工变更功能只记录在对象清单中，本期不配置菜单、不开放接口、不写对应表。

| 来源域 | 文件与数据类型 | JAR 中业务能力 |
|---|---|---|
| KEY | 一个 ZIP 中的收入、支出、库存、退库文本文件 | 上传、解压、识别文件、解析、入库、待处理、监控、代理国库配置 |
| TIMS | 收入、支出、库存 ZIP；内部为 Excel | 上传、解压、解析、入库、监控、自动处理、手动再次加工 |
| 公共 | 国库范围、日志、状态展示 | 查询、异常展示、删除、重试、手工下游加工调用 |

## 2. 已确认决策

1. 采用“并入 `org-tribe-system` 的独立数据上报模块”，不新建微服务。
2. 完整记录 JAR 中的全部代码能力；本期只启用原页面实际可用、原自动任务真实执行且依赖对象已确认的链路。未启用能力不得向未确认对象写数据。
3. 原始 ZIP 与解压后的文件都必须保留，支持追溯、下载和重新处理。
4. 自动执行严格停止在“解析及 STG 入库”；`adm.P_GUOKU_LIB_REPORT_ALL` 只能人工触发，不得由上传、定时扫描或任务恢复自动调用。
5. 人工调用和再次调用必须按本次上报批次记录的账期转为月末日执行；真实 ADM/ETL 依赖未核验时禁止调用并明确展示原因。
6. 当前使用菜单权限；设计中预留上报人员、审核/运维人员及全部按钮权限，后续启用时不改业务主体。
7. 所有确定与不确定事项均写入本文档和实施脚本；未确认的数据库对象不得猜测表结构或自行创建。
8. TIMS 同类型同周期重复上报沿用 JAR 的“整周期替换、后一次成功处理结果生效”；收入、支出、库存三类相互独立。
9. 技术异常采用用户确认的原子保护：整包失败回滚本次删除和写入，旧周期数据保持不变；不复制 JAR 捕获异常后提交部分数据的缺陷。
10. 上报服务器与数据库均采用保守限流：一个 TIMS 入库工作线程、一个 ZIP 一个业务事务、固定小批量写入、进度日志降频。

## 3. 架构选择

### 3.1 备选方案

| 方案 | 结论 | 原因 |
|---|---|---|
| 并入主系统的独立业务模块 | 采用 | 可复用主系统已有登录、菜单、审计、文件、任务、Vastbase 和 Vue 2 页面能力；当前页面规模与处理量无需独立部署 |
| 仓库内新增独立服务 | 不采用 | 需重复建设认证、权限、文件和调度，增加部署和运维成本 |
| 保持独立微服务 | 暂不采用 | 适合极大文件量或多系统复用场景；当前会增加网关、跨服务状态和授权复杂度 |

### 3.2 模块边界

后端在 `org.jeecg.modules` 下建立独立的 `reporting` 业务包，至少分为：批次与文件、KEY 解析、TIMS 解析、数据写入、下游加工、任务调度、过程日志和权限常量。前端在 `org-tribe-view` 下建立“数据上报”菜单域。

模块不直接依赖页面参数决定账期、目标表或过程名称；后台仅以已固化的批次、文件和任务记录执行。

### 3.3 性能影响与资源保护

该功能不要求独占服务器，也不需要一次把数万行或多个 Excel 全部放入 JVM 内存；正常情况下可与现有程序共同部署。主要压力集中在 Excel 解析的短时 CPU、归档与临时文件磁盘、以及 STG 周期删除和批量插入的数据库 I/O。为避免影响同机程序，实施时固定以下边界：

| 资源 | 控制方式 | 页面/运维可观察项 |
|---|---|---|
| CPU/JVM | TIMS 单工作线程、逐文件顺序解析、流式写临时文件，不缓存整包数据 | 当前文件、已解析行数、解析耗时、JVM 峰值压测结果 |
| 应用磁盘 | 上传前校验 ZIP 限额，解压时校验文件数和累计大小，入库前校验临时文件摘要与可用空间 | 原件大小、解压大小、临时文件大小、空间不足原因 |
| 数据库连接 | 一个任务只占用一个业务写连接；解析阶段不持有业务事务或表锁 | 等待入库、入库中、连接/锁等待耗时 |
| 数据库 I/O | 全包解析成功后才删除旧周期并按配置批量插入；初始批量 300～500 行，按内网压测调整 | 删除行数、尝试插入、已提交行数、批次数、提交耗时 |
| 并发 | 单实例和多实例都只允许一个 TIMS 入库任务执行；其他批次排队 | 排队序号、等待时间、当前执行批次 |
| 日志 | 行级错误按上限留样，进度按时间或行数降频写入，禁止每行写数据库日志 | 错误总数、错误样例、最后进度时间 |

原子替换会使数据库写入阶段持有一个较长事务，这是保证“旧周期不因失败而丢失”的必要代价。通过把 Excel 解析移到事务外、单线程串行、短批 SQL、上线前检查周期删除执行计划来缩短持锁时间。若生产 STG 缺少适合 `DATA_DATE` 条件的访问路径，必须先由内网 DBA 根据只读核对结果确认优化方式；程序不得自行创建索引或改变数仓分区。

## 4. 端到端业务流程

```text
上传 ZIP
  -> 原件归档并计算 SHA-256
  -> 建立上报批次和文件记录
  -> 安全解压并登记解压文件
  -> 后台按 JAR 固定列序解析 KEY/TIMS 文件
  -> KEY 按 JAR 各文件类型规则写对应明细
  -> TIMS 将规范化结果顺序写入批次私有临时文件
  -> TIMS 全包解析成功后开启单一业务事务
  -> TIMS 按 JAR 周期范围删除旧数据并分批写入 STG
  -> TIMS 核对行数并统一提交；失败则整包回滚
  -> 更新批次、文件、任务和时间线状态
  -> 授权人员按本批次周期人工调用 ADM（可选、受依赖门禁控制）
```

页面关闭不会取消后台任务。上传、解析、入库和人工加工均为可追踪任务；自动链路在 STG 入库成功后完成。任何阶段失败都停止后续依赖阶段，保留原件、批次、状态和异常信息，供授权人员按原批次重新执行。

### 4.1 批次状态

| 层级 | 状态 |
|---|---|
| 文件接收 | 待上传、上传中、已归档、上传失败 |
| 文件准备 | 待解压、解压中、解压成功、解压失败 |
| 数据解析 | 待解析、解析中、解析成功、解析异常 |
| 数据入库 | 待入库、入库中、入库成功、入库失败 |
| 下游加工 | 不需要、待人工调用、调用中、调用成功、调用失败、依赖未核验 |
| 整体批次 | 处理中、成功、部分成功、失败、已取消、已逻辑删除 |

整体状态由任务状态汇总，不由前端直接改写。每个状态变迁写入任务日志，记录开始时间、结束时间、耗时、当前文件、文件/行数统计、错误摘要及关联操作人。

## 5. JAR 全部业务功能与实现逻辑

本节以 JAR 控制器、定时配置、Mapper SQL 和静态页面为证据，列出完整业务功能。若后续样例、DDL 或过程定义证明具体字段口径不同，以补充材料为准，并在实施前更新本节。

### 5.1 KEY 文件上报与解析

1. 用户上传一个或多个 KEY ZIP。JAR 按 ZIP 基名检查是否已存在待处理记录；重复 ZIP 被拒绝并返回重复文件名。
2. 程序保存 ZIP、解压到独立目录，并从 ZIP 名称拆出业务日期与国库代码。JAR 将 ZIP 的路径、解压目录、上传人、上传时间、未处理状态写入 `agent_key_file.agent_keyfile_pending`。
3. JAR 在解压目录中识别 `.txt` 文件，并按文件名包含 `sr`、`zc`、`kc`、`tk` 分别识别为收入、支出、库存、退库；同时记录文件名及名称校验状态。
4. 定时解析待处理 ZIP。每种文本文件先按 ZIP 名删除对应历史明细，再将文本行拆分为字段集合并批量写入明细表。收入、支出、库存、退库的原始字段分别映射到：

| 类型 | 明细表 | JAR 写入字段 |
|---|---|---|
| 收入 | `agent_key_file.agent_file_income` | `D_ACCT`、`TRECODE`、`SUBJECT_CODE`、`TAXORGCODE`、`BUDGET_TYPE`、`LEVEL`、`F_AMT`、`YEAR_AMT`、`KEY_ZIP_NAME`、`ADD_TIME` |
| 支出 | `agent_key_file.agent_file_payout` | `D_ACCT`、`TRECODE`、`SUBJECT_CODE`、`TAXORGCODE`、`CODE_TYPE`、`LEVEL`、`F_AMT`、`YEAR_AMT`、`KEY_ZIP_NAME`、`ADD_TIME` |
| 库存 | `agent_key_file.agent_file_stock` | `D_ACCT`、`TRECODE`、`LEVEL`、`ACOUNT_CODE`、`F_BAL`、`YEAR_INIT_BAL`、`KEY_ZIP_NAME`、`ADD_TIME` |
| 退库 | `agent_key_file.agent_file_back` | `D_ACCT`、`TRECODE`、`SUBJECT_CODE`、`BUDGET_TYPE`、`LEVEL`、`TAXORGCODE`、`BCKREASON`、`F_AMT`、`YEAR_AMT`、`KEY_ZIP_NAME`、`ADD_TIME` |

5. 每个类型独立统计成功解析行数；解析异常分别写入 `SR_EXCEPTION`、`ZC_EXCEPTION`、`KC_EXCEPTION`、`TK_EXCEPTION`。所有类型完成后，待处理记录状态由未处理改为已处理。
6. 原页面可按 ZIP 名、状态、异常状态和国库范围查询待处理记录；可删除待处理记录及其归档 ZIP/解压目录。新实现改为逻辑删除、审计记录和受控物理清理。

### 5.2 代理国库配置与 KEY 监控

1. 代理国库配置维护 `TRE_CODE`、`TRE_NAME`、开始日期、结束日期、启停状态、创建/修改人和时间。
2. KEY 监控以代理国库配置为基线，关联 KEY 待处理记录，判断有效期内是否上报、是否有收入/支出/库存/退库文件、是否有解析异常。
3. 国库范围筛选依赖 `edw.cm_guoku_dimnsn` 的编码层级。JAR 通过当前选定国库的层级截取上级编码，再匹配下级 `TRE_CODE`；新实现必须保留等价范围语义，实际 SQL 以 Vastbase 对象结构确认后实现。

### 5.3 TIMS 上报、时间转换、固定列序与 STG 写入

1. 页面选择业务类型：`1=收入`、`2=支出`、`3=库存`，输入 `yyyy-MM` 账期并上传 ZIP。原页面文件名为“收入.zip”“支出.zip”“库存.zip”；新实现保留类型对应关系，并兼容 ZIP 根目录直接放 Excel 或先进入同名业务目录。
2. JAR 保存 ZIP 并在 `agent_key_file.tims_file_pending` 新增一条未处理记录。TIMS 汇总记录的 `TRE_CODE` 固定为 `2200000000`；这是原控制器的明确业务值，不使用当前登录人的国库前缀替换，也不按用户范围过滤 ZIP 内数据。用户国库范围只用于菜单、查询和监控展示。
3. 原 JAR 同时存在两条 TIMS 代码路径：未配置定时注解的 `TimsFileParseConfig` 写 `agent_key_file.tims_file_income/payout/stock`；真正由 `SCHEDULED_CRON` 每分钟执行的 `TimsAllFileConfig` 读取未处理记录并直接写三张 STG。用户已确认本期只复写真实自动链路，因此不向三张 TIMS 中间明细表写数据。
4. 自动 STG 路径按固定位置读取，不根据近似表头重新排列字段：

| 类型 | 固定列序（从第 1 列开始） | STG 目标 |
|---|---|---|
| 收入 | 日期、国库代码、国库简称、征收机关、预算级次、科目代码、科目名称、本期执行数、年累计 | `stg.trs_tmis_budget_income` |
| 支出 | 日期、国库代码、国库简称、预算级次、科目代码、科目名称、本期执行数、年累计 | `stg.trs_tmis_budget_payout` |
| 库存 | 日期、所属国库代码、所属国库名称、预算级次、借方发生额、贷方发生额、余额 | `stg.trs_tmis_stock` |

5. 时间转换严格分场景处理：页面 `BIZ_DATE=yyyy-MM`；删除和写入 STG 的 `DATA_DATE=yyyyMM`；`BATCH_DATE` 为实际执行日 `yyyyMMdd`；`D_ACCT` 保留 Excel 第 1 列按 JAR 读取后的原业务文本。已提供样例中收入/支出为 `202511`，库存为 `2025-11-01`、`2025-11-02` 等具体日期，库存日期不得改成月末或月份。
6. JAR 对数值单元格使用 `DecimalFormat("#.00")` 后交给数据库数值字段；迁移实现必须以目标 DDL 的 `numeric(...,2)` 结果为准并形成对照测试，不自行扩展金额精度。文本代码和日期保持原文本。
7. 自动任务处理完成后只更新本次 `tims_file_pending` 记录的状态和修改信息，不按 Excel 国库拆分、删除或重建历史 pending。详细文件数、尝试行数、提交行数和异常由新跟踪表表达。

### 5.4 TIMS 重复周期和整包事务

1. 原 JAR 不拒绝 TIMS 同周期重复上传。每次处理先按业务类型删除目标 STG 的本周期数据，再插入当前 ZIP 全部数据：收入/支出使用 `DATA_DATE=yyyyMM`，库存使用 `DATA_DATE LIKE 'yyyyMM%'`。
2. 因此重复周期是“同类型整周期替换，后一次成功处理结果生效”，不是追加、合并或按国库局部覆盖；三类业务互不影响。
3. 新实现保持上述成功路径结果，但修正 JAR 捕获异常后可能提交删除或部分插入的缺陷：一个 ZIP 中的全部 Excel 是一个提交单元。解析、删除、所有批次插入、行数核对和成功终态必须统一提交；任一失败整包回滚，旧周期数据保持不变。
4. 为控制资源，先逐个 Excel 解析并把规范化结果顺序写入批次私有临时文件；全包成功后才开启业务事务，从临时文件每批读取固定数量写入。临时文件不进入数据库业务表，权限限于服务账号，成功或失败后删除。
5. 同周期并发任务必须串行，且为保护共享服务器，本期所有 TIMS 入库任务全局串行。新建 `agent_key_file.report_runtime_lock` 保存固定的 TIMS 租约记录；执行器先用短事务原子领取租约，业务事务再锁定并校验同一租约令牌后执行删除和插入。租约领取、续租、失权和崩溃恢复 SQL 必须先通过 Vastbase G100 V2.2 核验；旧执行者失权后不得提交，一个任务失败回滚后等待任务才能继续。
6. 自动入库执行器固定为一个工作线程；批量大小、ZIP 大小、解压总量和进度日志频率均配置化。进度展示使用“已处理/待提交”，只有业务事务提交后才能显示“已入库”。

### 5.5 TIMS 监控、手工加工与再次调用

1. TIMS 监控以代理国库配置和 TIMS 待处理记录为基线，显示各国库在有效期/账期内收入、支出、库存是否均已上报、是否已处理、是否存在异常，并支持按国库、名称、文件、账期、上报状态筛选。
2. JAR 提供“手动跑数”，接收 `yyyy-MM`，转为当月最后一天，并调用 `adm.P_GUOKU_LIB_REPORT_ALL(账期)`。
3. 调用前，JAR 查询 `etl.guoku_lib_report_all_log` 中 `STATE='1'` 的记录；若已有运行中任务，拒绝再次调用。否则写入一条“运行中”过程日志并调用过程。
4. ADM 调用严格保持手工触发。自动链路在 STG 入库成功后结束并显示 100%；页面单独显示“待人工加工/依赖未核验/调用中/成功/失败”。授权人员可按本批次账期再次调用，但不能从前端传入其他周期。
5. `etl.guoku_lib_report_all_log` 真实 DDL、列顺序和 `adm.P_GUOKU_LIB_REPORT_ALL` 定义未确认前，按钮不可执行；不得使用模拟表或空过程伪装生产成功。

### 5.6 收入/支出变更记录（JAR 存在、本期不启用）

1. 原页面可查询 `edw.income_report_detail_stat` 和 `edw.payout_report_detail_stat` 的明细，并按国库、账期、统计代码、预算级次筛选。
2. 查询时叠加 `edw.reprot_update_record` 中最近一次人工调整后的金额；其中 `type` 区分 `income` 与 `payout`。
3. 用户可新增变更记录，保存原金额、新金额、差额、账期、国库、统计代码、预算级次、类型、变更日期和变更人。
4. 原静态页面中的“TIMS数据更改”和“更改记录”按钮已被注释，提供的开发/生产对象中也没有三项 EDW 依赖。本期不配置该菜单、不开放控制器和接口、不查询或写入上述三对象；后续取得真实 DDL 并由用户单独确认后再启用。

### 5.7 JAR 页面、接口与迁移去向

| JAR 功能入口 | 原能力 | 新模块去向 |
|---|---|---|
| KEY 待处理页面 | ZIP 上传、列表、删除、异常展示 | 上报列表/KEY 详情 |
| TIMS 待处理页面 | 单 ZIP 上传、类型/账期、列表、删除、手动跑数 | 上报列表/TIMS 详情/手工加工任务 |
| KEY 监控页面 | 国库上报与异常监控 | 上报监控 |
| TIMS 监控页面 | 收入支出库存齐全性、异常、上报状态 | 上报监控 |
| 代理国库设置 | 配置及启停 | 代理国库配置 |
| 数据变更弹窗/记录 | 收入支出查询与变更记录；原按钮已注释 | 本期不配置菜单、不开放接口 |

原 JAR 的 `/exeTimsFile` 页面调用在控制器中不存在，且上传路径与 Excel 解析路径存在不一致。本设计不保留该失效接口，改为批次任务编排；该改造保持“上传后自动处理”的业务语义。

### 5.8 自动入库、手工加工与重试实现规范

- 上传完成后自动提交解析及 STG 入库任务；无论 ADM/ETL 契约是否确认，均不得自动提交过程调用任务。
- 下游调用参数从批次读取，不允许前端随意传入其他期间。
- 原 JAR 调用过程的规则：把 `yyyy-MM` 转为当月最后一天，再调用 `adm.P_GUOKU_LIB_REPORT_ALL(账期)`。
- 重试可按失败阶段发起：重新解析、重新入库、人工再次加工；每次均新建任务执行记录并关联原批次。同阶段已排队/执行时拒绝重复提交。
- 任务以数据库为事实源，事件只用于低延迟唤醒；执行时按唯一任务 ID 原子领取，每次领取生成唯一租约令牌。TIMS 解析在业务事务外完成；周期删除、全部 STG 插入、行数核对、原 pending 成功状态和任务业务终态在同一事务内校验租约并提交，旧执行者失权后不能提交。定时恢复重启后的 `QUEUED`；解析/入库进程中断后可重新排队，加工任务租约超时只置失败，禁止自动重放外部过程。
- 手工加工按过程名称全局互斥，防止多实例并发重复处理。原 JAR 的 ETL `STATE='1'` 检查仍保留；在真实 ETL 日志 DDL 和陈旧锁处理规则确认前，不猜测或自动清理外部运行状态，生产按钮由依赖门禁保持不可执行。

## 6. 文件归档与解析规范

### 6.1 文件归档

文件二进制不存入数据库。服务端生成目录，不接受前端路径：

```text
<归档根目录>/reporting/<source-domain>/<accounting-period>/<batch-id>/
  original/       原始 ZIP
  extracted/      解压文件
  work/           解析成功后、入库完成前的私有临时结果
  manifest.json   文件清单、摘要、处理结果快照
```

数据库保存原始名、归档名、相对路径、大小、SHA-256、父子文件关系、留存状态与逻辑删除状态。`work` 目录不是业务留存，文件权限限于服务账号，任务成功、失败或恢复清理后删除；开始数据库事务前必须检查所需空间和文件摘要。物理清理由独立保留策略任务执行，不由普通删除操作直接删除。

### 6.2 解压安全与兼容性

- 拒绝路径穿越、损坏 ZIP、超过配置数量/大小限制和不允许的文件类型；
- 递归扫描所有子目录；只把允许的 `.txt`、`.xls`、`.xlsx` 交给对应解析器；
- 忽略 `__MACOSX`、`.DS_Store`、`._*` 等 macOS 附属文件；
- 同时兼容 ZIP 根目录直接放业务文件、以及业务文件位于收入/支出/库存等子目录；
- 文件类型、压缩包声明类型、内部文件内容不一致时，记录明确异常。

已核对根目录下三个脱敏样例：`收入.zip` 含收入目录和 4 个 `.xls`，`支出.zip` 含支出目录和 2 个 `.xls`，`库存.zip` 含库存目录和 3 个 `.xls`；每个工作簿当前均有一个业务工作表，且 ZIP 含 macOS 元数据目录。原 JAR 自动任务按固定业务目录使用 `File.list()`，不能处理任意层级；新实现完整递归收集业务文件，同时保持固定列序和字段结果。

### 6.3 待样例验证项

KEY 收入/支出/库存/退库样例仍待补充。现有 TIMS 样例足以确认目录、工作表、固定列序和时间文本，但脱敏值不能反推出新的业务校验规则。需继续核验：生产最大文件/行数、金额舍入口径、空值和异常行表现。

## 7. 页面与权限规范

### 7.1 页面

1. **上报列表**：批次号、来源域、类型、账期、国库范围、文件、发起人、当前阶段、整体状态、进度、耗时和操作入口。
2. **上报详情**：按时间线展示上传、解压、解析、待提交、入库以及独立的手工加工；展示每步文件数、处理行数、已提交行数、错误、调用参数、开始/结束时间和结果。
3. **文件与异常明细**：原件/解压文件下载、文件解析结果、行级错误。
4. **KEY 代理国库配置**：保留原启停、有效期和查询能力。
5. **上报监控**：保留原 KEY/TIMS 齐全性、处理状态和异常监控；本期不展示收入/支出变更记录。

前端异步轮询批次详情；任务完成、失败或进度变化均刷新状态。后续可在不改变任务模型的前提下替换为 WebSocket 推送。

当前菜单权限为最小上线控制。服务端从 `sys_user.guoku_id` 派生查询和监控范围；TIMS ZIP 内容及固定汇总 pending 不得用该范围裁剪。保留以下按钮权限编码和校验点：

| 权限编码类别 | 预留操作 | 后续角色建议 |

| 文件 | 上传、查看、下载、逻辑删除、物理清理 | 上报人员；审核/运维人员；管理员 |
| 任务 | 重新解析、重新入库、人工加工/再次加工、取消 | 审核/运维人员 |
| 配置 | 代理国库配置、保留策略 | 管理员 |
| 审计 | 查看完整异常、调用参数、任务日志 | 审核/运维人员、管理员 |

初期可将所有操作授权给同一菜单角色；后续启用按钮权限时，只增加菜单/按钮数据与角色授权，不改控制器、任务或页面业务逻辑。

## 9. Vastbase 脚本交付边界

### 9.1 开发环境模拟 DDL

在开发环境缺少原数仓对象时，可使用 [`2026-07-25-agent-key-file-handler-vastbase-simulation.sql`](2026-07-25-agent-key-file-handler-vastbase-simulation.sql) 创建可运行的最小模拟对象。该脚本依据 JAR 的 Mapper、配置和反编译结果反推，不是原库 DDL，也不能替代内网核对。

模拟脚本保留 JAR 明确对象的最小结构，供隔离开发库进行 SQL 兼容性和任务状态测试。它刻意将所有无法从 JAR 确认的字段长度、金额精度、主键、索引、分区和过程逻辑视为假设；内网验证后必须用真实 DDL 及过程定义替换。生产部署脚本不得创建 `edw.income_report_detail_stat`、`edw.payout_report_detail_stat`、`edw.reprot_update_record`、`etl.guoku_lib_report_all_log` 或 `adm.P_GUOKU_LIB_REPORT_ALL`，也不得以模拟对象通过依赖门禁。

模拟过程只输出调用通知，不执行真实数据加工，只允许在独立模拟库验证调用路径；它不能用于业务验收，页面也不能把模拟返回展示为真实加工成功。

脚本均在文件头写明目标 Schema、对象、执行前提、是否 DDL、是否允许重复执行和回滚方式。脚本分为：

```text
01_schema_object_inventory.sql
02_agent_key_file_structure_check.sql
03_stg_structure_check.sql
04_edw_etl_adm_dependency_check.sql
05_report_tracking_tables.sql
06_report_indexes_constraints.sql
07_mysql_vastbase_sql_compatibility_check.sql
08_data_reconciliation_check.sql
09_menu_permission_seed.sql
10_process_dependency_check.sql
11_rollback.sql
12_stg_performance_check.sql
```

在既有 JAR 表 DDL 未确认前，脚本只生成核对报告，不覆盖或修改现有业务对象。`12_stg_performance_check.sql` 只读核对三张 STG 的索引、分区、统计信息和周期删除执行计划；未经内网核对不得自动建索引或调整分区。

本模块新增七张技术跟踪表，全部固定归属 `agent_key_file`，不加入 ODS/EDW/ADM 业务分层：

| 新表 | 用途 | 是否写业务明细 |
|---|---|---|
| `report_batch` | 一次上传批次、来源、类型、账期、整体状态和汇总计数 | 否 |
| `report_file` | ZIP、解压文件、摘要、路径、文件级结果 | 否 |
| `report_task` | 解析、入库、手工加工任务及租约令牌 | 否 |
| `report_task_log` | 阶段时间线和降频进度 | 否 |
| `report_parse_error` | 有上限的行级错误样例和错误总数关联 | 否 |
| `report_process_call` | 人工 ADM 调用参数、结果和审计 | 否 |
| `report_runtime_lock` | TIMS 全局单执行租约；防止多实例同时解析/入库 | 否 |

七张表只承担新页面的状态、审计、恢复和并发控制；JAR 的业务明细仍只写已确认的原目标表，不把临时解析数据写入新表。

转换规则包括：MySQL 反引号、`IFNULL`、`DATE_FORMAT`、`LIMIT offset,size`、`GROUP_CONCAT`、`FIND_IN_SET` 等语法改为 Vastbase 兼容 SQL；所有 `${}` 动态拼接改为白名单对象路由和参数绑定。

## 10. 验收与回滚

### 10.1 新旧对照验收

- 以脱敏样例和后续补充样例分别验证 KEY 与 TIMS 全部类型；
- 核对固定列序、文件数、解析成功/失败行数、`D_ACCT` 原文、`DATA_DATE=yyyyMM`、`BATCH_DATE=执行日`、固定汇总国库代码、金额、目标表行数和人工加工结果；
- 验证根目录与多级目录、macOS 附属文件、重复上传、错误文件、入库失败和重试；
- 验证同类型同周期再次上报是整周期替换，收入、支出、库存互不覆盖；
- 注入“删除后失败”“中间批次插入失败”“提交前行数不一致”等故障，确认业务事务全部回滚且旧周期数据、原 pending 记录保持不变；
- 使用多 Excel、单文件数万行的规模样例验证顺序解析、临时文件、300～500 行初始批量、单入库工作线程、内存峰值、临时磁盘占用和数据库执行计划；批量大小最终以压测结果配置，不写死在业务代码；
- 验证页面区分“已解析/待提交/已提交”，只有事务提交后显示入库成功；验证自动链路不会创建 ADM 调用任务；
- 验证菜单可见性、未来按钮权限切换点和全链路操作日志；
- 由数据核对 SQL 对比迁移前后关键行数、金额汇总和异常数。

### 10.2 上线与回滚

- 上线前先以只读核对脚本确认对象与过程依赖；
- 先灰度执行一批脱敏/可回放文件，核对通过后只开启上传后的自动解析和 STG 入库；ADM 始终保持人工触发；
- 灰度期间固定单工作线程，观察应用堆内存、CPU、归档/临时磁盘、数据库锁等待、删除与插入耗时；超过配置阈值时停止领取新任务，不中断正在提交的事务；
- 失败时停止新任务投递，不删除原件和批次记录；
- 数据写入使用批次和任务边界控制，回滚脚本仅处理新模块创建的对象及可识别的新批次数据，不直接清理既有数仓对象。

## 11. 明确不迁移的旧实现缺陷

- TIMS 页面调用但 JAR 控制器不存在的 `/exeTimsFile` 接口；
- 目录递归仅返回最后一层文件数组、可能遗漏 Excel 的实现；
- 前端同步阻塞上传/调用；
- SQL 中 `${}` 直接拼接和 MySQL 专有函数；
- 仅以“已处理/未处理”表达过程状态，无法展示完整进度；
- 删除旧周期后捕获异常仍可能提交删除或部分数据；
- 硬编码文件路径、账号口令及外部服务地址。

固定汇总国库代码 `2200000000` 不属于待修复缺陷，必须按 JAR 保留。上述技术修正不改变原始业务口径；新模块以批次、文件、任务和过程日志实现等价且可审计的业务结果。
