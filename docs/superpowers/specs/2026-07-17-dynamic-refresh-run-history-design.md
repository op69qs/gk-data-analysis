# 动态刷数运行记录与启动反馈设计

## 背景

动态刷数页面已恢复列表、维护和异步启动能力，但现有实现仍有三个问题：

1. 表格同时启用了横向滚动和固定右侧操作列，Ant Design Vue 会单独渲染固定列，宽屏下出现空白分隔和视觉错位。
2. `/errorLogController/callProc` 只完成任务状态切换和异步提交，却返回“启动成功”，容易被理解为任务已经执行成功。
3. `adm.exec_shell_task` 只能保存任务的最后状态，无法查询每次启动时间、运行结果和失败原因。
4. 动态刷数组件错误地内嵌了“报告管理”标签页；报告管理不属于该菜单页面。

生产 JAR 可确认原有启动流程和存储过程调用约定，但不包含运行记录功能。本设计保留 JAR 的业务约定，并由当前应用独立实现运行记录。

## 目标

- 修复动态刷数主列表的列错位。
- 移除动态刷数页面内部多余的“报告管理”标签页。
- 每次成功受理启动请求时创建独立运行记录。
- 在任务操作栏提供“运行记录”入口和分页弹窗。
- 清楚区分“任务已提交”和“任务执行成功”。
- 成功记录执行结果；失败记录异常类型、错误信息和根因。
- 存储过程调用严格保持生产 JAR 的两个参数约定：`shell_param` 和任务 `id`。
- Mapper 和服务集成测试连接真实 MyBatis 与 Vastbase，不使用 Fake Mapper。

## 不在本次范围内

- 不读取或依赖未知的生产 ETL 错误日志表。
- 不修改门户菜单、动态路由或权限属性。
- 不增加定时调度、日志清理策略或跨任务运行记录总览。
- 不改变动态刷数页面现有路由路径和五个业务字段。

## 方案选择

采用应用自有的独立运行记录表。

不把历史记录追加到 `adm.exec_shell_task`，因为该表代表任务当前配置和最后状态，不能自然表达一对多历史。不复用系统日志或 ETL 日志，因为它们无法稳定按本次启动关联，且生产结构未提供。

## 数据设计

新增 `adm.exec_shell_task_run_log`。所有 schema、表名和字段名使用未加双引号的小写标识符，符合 Vastbase 默认折叠规则。

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | `varchar(40)` | 本次运行记录主键 |
| `task_id` | `varchar(40)` | 动态刷数任务 ID |
| `task_name` | `varchar(255)` | 启动时任务名称快照 |
| `task_type` | `varchar(2)` | 启动时任务类型快照 |
| `shell_path` | `varchar(255)` | 启动时脚本路径快照 |
| `shell_name` | `varchar(255)` | 启动时脚本或存储过程名称快照 |
| `shell_param` | `varchar(1000)` | 启动时参数快照 |
| `status` | `varchar(3)` | `1` 执行中、`200` 成功、`500` 失败 |
| `start_time` | `timestamp(0)` | 接受启动请求的时间 |
| `end_time` | `timestamp(0)` | 执行结束时间，执行中为空 |
| `result_message` | `text` | 成功摘要或失败日志 |
| `create_user` | `varchar(128)` | 启动用户，可为空 |

创建以下索引：

- `(task_id, start_time desc)`：运行记录弹窗按任务倒序查询。
- `(status)`：便于后续排查执行中或失败记录。

运行记录保存任务配置快照，因此任务后续被修改时，历史记录仍能说明当次实际执行内容。任务删除时不级联删除运行记录；本次页面不增加已删除任务的历史查询入口，但数据库审计记录仍保留。

数据库脚本包含两部分：

1. 在完整初始化脚本中加入新表，供新环境部署。
2. 提供只创建新表和索引的幂等增量脚本，供当前 `gk_data_analysis` 数据库执行，禁止通过重跑完整 ADM 初始化脚本升级现有库。

## 后端设计

### 接口

保留现有接口并新增运行记录查询：

- `POST /errorLogController/callProc`
- `POST /errorLogController/getRunRecords`

`getRunRecords` 请求参数：

- `task_id`：必填。
- `pageNo`：默认 1。
- `pageSize`：默认 10。

响应继续使用项目现有格式：

```json
{
  "result": "success",
  "msg": "查询成功",
  "rows": [],
  "total": 0
}
```

`callProc` 成功受理后的响应为：

```json
{
  "result": "success",
  "msg": "任务已提交，请在运行记录中查看执行结果",
  "runId": "本次运行记录ID"
}
```

这里的 `success` 只表示请求受理成功，不表示后台任务执行成功。最终结果以运行记录和任务状态为准。

### 启动事务

启动服务按以下顺序执行：

1. 校验任务 ID。
2. 通过条件更新将任务状态原子地改为 `1`，拒绝重复启动或已删除任务。
3. 按任务 ID 从数据库读取完整任务。
4. 插入状态为 `1` 的运行记录和任务配置快照。
5. 提交异步执行，传递 `taskId` 与 `runId`。

任务状态切换和运行记录插入通过 `TransactionTemplate` 位于同一数据库事务中。只有该事务提交完成后才向异步执行器提交任务，避免后台线程先于事务提交而查询不到任务或运行记录。若异步执行器拒绝任务，则通过独立的补偿更新立即把任务和运行记录改为 `500`，记录提交失败原因，并让接口返回失败。

### 存储过程执行

存储过程调用保持生产 JAR 约定：

```text
call schema.procedure(shell_param, task_id)
```

- 过程名只允许合法的 `schema.procedure` 格式，并按 Vastbase 未加引号的小写标识符规则执行。
- `shell_param` 和 `task_id` 使用 JDBC 绑定参数。
- 不再按 `@` 拆分存储过程参数。
- 调用前任务状态已经是 `1`。
- 调用正常返回后重新读取任务状态：
  - 状态为 `500` 时，保留失败状态，不得覆盖成 `200`。
  - 状态为 `200` 时，运行记录记成功。
  - 状态仍为 `1` 时，由执行器补写任务和运行记录为 `200`，兼容不主动更新状态的过程。
- Java/JDBC 抛出异常时，任务和运行记录均更新为 `500`。

失败日志由应用生成，不依赖 ETL 表。内容包括异常类型、异常消息和最深层根因。为避免超大异常内容占用数据库，`result_message` 最多保存 64 KiB，超出部分截断并标注。

### 脚本执行

- 沿用安全的参数列表启动方式，不通过 shell 拼接执行。
- 退出码为 `0` 时记录成功和退出码。
- 非零退出码记录失败、退出码和截断后的标准错误。
- 启动异常、中断和超时记录对应异常类型、消息和根因。
- 标准错误最多保存 64 KiB。

### 状态一致性

每次执行只有一个 `runId`。执行器在同一个完成路径中更新任务最后状态和对应运行记录：

- 成功：任务 `200`，运行记录 `200`，填写 `end_time`。
- 失败：任务 `500`，运行记录 `500`，填写 `end_time` 和失败日志。

如果运行记录更新失败，服务端记录带 `taskId`、`runId` 的错误日志；不得把任务失败改成成功。任务当前状态仍作为主列表的兜底结果。

## 前端设计

### 主列表对齐

- 移除页面内部的 `a-tabs`、`ReportManagement` 组件导入和“报告管理”标签页，动态刷数菜单打开后直接展示任务查询区与列表。
- 移除固定右侧操作列和与其配套的横向滚动设置，避免固定列克隆与主体表格分离。
- 使用固定表格布局、明确列宽和内容省略提示。
- 操作列宽度增加以容纳“修改 / 启动 / 删除 / 运行记录”。
- 主列表业务字段顺序保持生产截图不变。

### 启动反馈

确认启动后：

- 接口成功受理时使用信息提示：“任务已提交，请在运行记录中查看执行结果”。
- 不使用成功提示，不宣称后台执行已经完成。
- 刷新主列表，使状态显示为“正在执行”。
- 不在主页面轮询并弹出最终结果，避免长任务造成页面计时器和重复提示；用户通过运行记录查看结果。

接口受理失败时显示真实失败消息，例如任务正在执行、任务不存在或线程池拒绝提交。

### 运行记录弹窗

操作栏增加“运行记录”。点击后打开只读分页弹窗，标题包含任务名称，显示：

- 启动时间。
- 结束时间。
- 运行状态。
- 执行结果。

运行状态使用与主列表一致的标签。成功结果显示成功摘要；失败结果以可换行、可复制的预格式文本显示完整错误摘要。弹窗每次打开和翻页都调用真实分页接口。

## 错误处理

- 非法过程名在异步执行阶段失败，运行记录写入 `IllegalArgumentException` 及“存储过程名称不合法”。
- JDBC 调用错误记录 SQL 异常类型、消息和根因，不向页面返回数据库连接凭据。
- 过程内部把任务状态写为 `500` 但未向 JDBC 抛出异常时，运行记录写入“存储过程返回失败状态（500）”；不伪造未知 ETL 错误详情。
- 脚本非零退出记录退出码和标准错误。
- 查询运行记录失败时弹窗显示错误提示并清空列表，不展示旧任务的数据。

## 测试设计

### 真实 Vastbase 集成测试

使用 Spring Boot、真实 MyBatis Mapper 和当前 Vastbase：

- 新增、按任务分页查询和更新运行记录。
- 验证所有返回字段名为小写。
- 验证 `(task_id, start_time)` 查询顺序。
- 使用非法存储过程名称启动临时任务，等待真实异步执行完成，断言：
  - 任务最终状态为 `500`。
  - 对应运行记录最终状态为 `500`。
  - `end_time` 非空。
  - `result_message` 包含异常类型和“存储过程名称不合法”。
- 每个测试使用唯一 ID，并在 `finally` 中删除测试任务和运行记录；可回滚的同步 Mapper 测试继续使用事务回滚。

删除依赖 Fake Mapper 的 Service 和 TaskRunner 测试。纯字符串校验、参数构造等不访问 Mapper 的单元测试可以保留，因为它们不伪造数据库行为。

### 前端和浏览器验证

- Vue 2 编译和生产构建通过。
- 使用真实浏览器登录当前系统，确认主列表表头和值对齐，无固定列空白。
- 确认动态刷数页面只显示任务查询与列表，不再出现“报告管理”标签。
- 点击启动后只显示“任务已提交”信息提示。
- 打开运行记录弹窗，确认真实网络请求、分页和字段展示。

- 检查浏览器 Console、接口响应和 Java 后台日志。

## 部署与兼容

- 先执行增量 DDL，再部署包含新 Mapper SQL 的后端，最后更新前端静态资源。
- 完成 Maven 打包后更新 `deploy-package/app/org-tribe-system-2.1.0.jar` 并重启服务。
- 验证五个既有接口和新运行记录接口均已映射。
- 菜单路径、组件路径、路由、门户权限属性和现有任务数据均不变。

## 验收标准

- 主列表不存在表头、数据或操作列视觉错位。
- 动态刷数页面不再出现“报告管理”标签页。
- 每次成功受理启动请求只生成一条运行记录。
- 接口和页面不再把“已提交”描述成“执行成功”。
- 执行成功、Java/JDBC 异常、脚本非零退出、存储过程内部返回 `500` 均能形成准确的最终记录。
- 非法存储过程测试通过真实 Mapper 和 Vastbase，运行记录包含可读错误信息。
- 页面、后端、数据库脚本、部署 JAR和运行中服务保持一致。
